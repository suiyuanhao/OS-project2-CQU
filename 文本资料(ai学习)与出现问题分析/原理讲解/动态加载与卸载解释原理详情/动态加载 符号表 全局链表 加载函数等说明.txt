# 深度解析：Linux 内核模块（LKM）的动态加载、重定位与符号表机制

## 一、 核心概念：什么是内核模块（LKM）？
Linux 内核（宏内核架构）为了保持极致的轻量与灵活，将大量非核心功能（如硬件驱动、特殊文件系统）从内核主体中剥离。这些功能被编译为独立的 `.ko`（Kernel Object）文件，在需要时通过 `insmod` 动态插入内核空间，不需要时通过 `rmmod` 动态卸载。这就是 LKM（Loadable Kernel Module）机制。

## 二、 编译期：`.ko` 文件里到底装了什么？
当我们执行 `make` 时，编译器（如 `rustc` 或 `gcc`）依据编译原理，将源码翻译成机器码并打包成 `.ko` 文件。`.ko` 内部主要包含：
1.  **代码段（Code Section）**：函数编译后的二进制机器指令。
2.  **数据段（Data Section）**：全局变量的初始值和内存分配信息。
3.  **符号表（Symbol Table）**：记录了所有函数和变量的**相对偏移量**（例如：`init` 函数在文件头往下偏移 1024 字节）。
4.  **元数据段（`.modinfo`）**：由 `module!` 宏生成的模块名称、作者、许可证等信息。

> **核心难点**：在编译期，编译器**并不知道**这个模块未来会被加载到内核物理内存的哪个地址，因此符号表中只能记录相对偏移量，无法记录绝对物理地址。

## 三、 加载期：`insmod` 到底做了什么？（重定位机制）
当用户态执行 `sudo insmod xxx.ko` 时，会触发系统调用（`init_module`），内核接管并执行极其严密的装载过程：

1.  **分配地盘**：内核在 Ring 0 特权级的内存空间中，为模块分配一块内存，并获得一个**“头地址（Base Address）”**。
2.  **加载机器码**：将 `.ko` 文件中的代码段和数据段拷贝进这块分配好的内存中。
3.  **提取身份**：扫描元数据段，提取纯名字（如 `rust_hello`），作为该模块在内核全局链表中的唯一登记名。（这就解释了为什么 `rmmod` 只需要纯名字，不需要 `.ko` 后缀）。
4.  **重定位（Relocation）**：这是最核心的一步。内核将符号表中的**“相对偏移量”**加上刚分配的**“头地址”**，计算出函数和变量在内存中的**真实绝对地址**，并将其回填到代码中。
    *   *公式：真实地址 = 头地址 + 相对偏移量*
5.  **回调入口**：地址就位后，内核找到 `init` 函数的真实地址，主动跳转执行。

## 四、 符号解析与全局链表：为什么跨模块调用需要依赖顺序？
每一个被加载进内核的模块，其符号表（记录了函数和变量的真实内存地址）都会被内核挂载到一个**全局符号链表**中。

*   **如果被调用的模块已加载**：内核在全局链表中能找到该函数的真实地址，完成符号解析，调用成功。
*   **如果被调用的模块未加载**：内核在全局链表中查无此人，直接报错 **`Unknown symbol`**，拒绝加载当前模块。
*   **权限隔离**：内核模块运行在内核态（Ring 0），无法直接调用处于用户态（Ring 3）的代码。所有模块必须在同一内存空间（内核态）中，才能通过全局符号链表进行互相调用。

## 五、 卸载期：`rmmod` 是怎么清理战场的？
1.  用户态执行 `sudo rmmod <模块名>`。
2.  内核根据纯名字，在全局模块链表中找到对应的 `struct module` 节点。
3.  内核执行模块的退出函数（C 语言的 `__exit`，或 Rust 的 `Drop` 机制）。
4.  根据符号表，将当初分配的那块内存彻底释放，并从全局链表中删除该节点。模块在内核中彻底消失。

## 六、 核心汇报金句（建议背诵）

> “老师，通过推导这套底层机制，我深刻理解了内核模块的运行原理。
> 
> `.ko` 文件本质上是一个未定址的二进制代码包，里面不仅有函数和变量的机器码，还有记录相对偏移量的符号表。当我们执行 `insmod` 时，内核不仅为其分配了内存，更完成了一次精密的**重定位**——将头地址与偏移量相加，算出绝对地址，并挂载到内核的全局符号链表中。
> 
> 只有挂在全局链表中，模块才能被系统识别，才能解决跨模块调用的符号依赖问题。而在卸载时，内核通过元数据中的名字精准定位，释放内存并摘除链表节点。
> 
> **这套从编译期偏移、到加载期重定位、再到运行期全局链表挂载的机制，就是 Linux 实现动态插件生态的底层基石。**”
